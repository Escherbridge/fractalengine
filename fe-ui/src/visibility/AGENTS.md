# Visibility registry admission

Group rename, visibility, create and reorder proposals use `ComparePetalVisibilityGroups` with the exact last confirmed DTO vector. Stored order numbers are retained in the expected snapshot. The display changes only when an authoritative registry reply arrives; queue admission is never presented as persistence. The active Petal and Editor gates are repeated at action admission, while the transaction checks actual authority.

Registry commands use nonblocking channel admission. Full or disconnected queues leave no pending write. An accepted write retains ownership through an unknown outcome; the read-only Check stored Groups action queues one correlated current read after the original command, never replays that command, and releases ownership only on the matching write/read reply. Unrelated registry snapshots update the confirmed display without releasing ownership. Failed reads can be retried explicitly; a missing pure-read reply expires its coalescing wait after 15 seconds, permitting another read without replaying any write. An expired read still blocks competing registry edits until a reply or explicit read failure releases it. Navigation discards the previous Petal's view/request state, without claiming its accepted write was rolled back.

Registry CAS cannot remove IDs because that would orphan memberships. The typed Group Delete action instead captures all authoritative stored members independently of selection, cleans memberships and registry in one transaction, and records one exact proven inverse, including empty Groups and zero-node Petals. Restoring a deleted ID requires its immutable original checked-delete proof; it is not a registry CAS loophole. Scope-eye and legacy per-node membership helpers keep their existing behavior. See `../editor_batch/AGENTS.md` and `../../../fe-database/src/handlers/editor_batch/AGENTS.md` for transaction/replay boundaries.
