## Sim (I-SIM)

- R-TOOL-14 FIXED `tools/qa/sim/driver.py` `accept_extension` posted to `/api/v1/extensions/{installation}/accept`, which is no route (fe-api's verbs are consent, bind, unbind, enable, disable, update). governance.md §Audit: local acceptance in a verse is `bind` with `verse_id` set; the op now posts that, carrying an optional `source_class` pick (bindings.md §5.3).
- R-TOOL-15 KEPT the other ext ops match fe-api `extensions::routes` and `bindings::routes`: install `POST /api/v1/extensions`, consent and bind `POST .../{installation}/{verb}`, policy `PUT /api/v1/verses/{v}/extension-policy`, command `POST /api/v1/petals/{p}/extensions/{pkg}/commands/{c}`, ingress `.../ingress/{endpoint}`, bindings `PUT|DELETE /api/v1/bindings`. `extension_command` with `door: ws` is recorded as REST standing in for WS (honest, no WS client yet).
- R-TOOL-16 KEPT named queries `fleet_readings` and `device_readings` are shaped by the prober (`NAMED_QUERIES`), never SQL from a scenario; the fe-api query guard errors past its row cap rather than truncating, so `count` and `count_by_device` cannot be silently short.
- R-TOOL-17 FIXED `tools/qa/sim/prober.py` `_named_query`: the petal id and package id were interpolated raw into SurrealQL (`'%s'`); they are now escaped string literals, as `driver.surreal_string` does.
- R-TOOL-18 KEPT `tools/qa/sim/loopback.py`: the static site, HTTP sink and MQTT broker all bind `LOOPBACK_HOST = "127.0.0.1"`; `probe_port` connects to loopback only. The host admits those endpoints because their configured base is itself internal (`sources.rs` `base_is_internal`, `net/connect.rs` loopback plaintext rule).
- R-TOOL-19 FIXED `loopback.py`: one key signed both the index and the revocation list and was written as the trust root. fe-hexon `verify_index` refuses an index whose signer is a trust root (`IndexKeyMisused`, store-client steer 20:45), so the first served index would be refused. The run now has two seeded keys: `fe-sim-index`, pinned per source in `extension_sources.json`, and `fe-sim-revocation`, the trust root with `revocation = true`.
- R-TOOL-20 FIXED `loopback.py` trust file `role = "dev"`: a dev root loads only with `FE_EXT_DEV=1` in a debug build (`trust_roots.rs:109-128`), so a release QA stage dropped it and never accepted a revocation list. It is now `role = "publisher"`, in a run-scoped config dir only.
- R-TOOL-21 FIXED `tools/qa/sim/run.py`: `loopback.describe()` produced a trust file nobody wrote, so peers never trusted the run's keys. `stage_extension_config` writes `trusted_publishers.toml` and `extension_sources.json` under `<run>/extensions` and exports `FE_EXT_CONFIG_DIR` before `peers.ps1 Start` (launch.ps1 sets its overrides on the process env, so peers inherit it). It also sets `FE_EXT_REVOCATION_PULL_SECS=10`: the 15-minute default meant `publish_revocation` in ext-fleet and ext-bindings could never land inside a run.
- R-TOOL-22 FIXED `run.py`, `scenario.py`, `scenario.schema.json`: per-peer local policy had no harness path (ext-bindings called an assumed `PUT /api/v1/extensions/local-policy`; no such route; governance reads `extensions.toml` at startup only). New `peers[].extension_policy: {deny: [ids]}` stages that peer's own config dir; it loads at the peer's next host `restart` op (`Host.peer_env`), and `scenario.py` refuses a declared policy with no restart for that peer (mutation-checked). Schema regenerated.
- R-TOOL-23 HANDED-OFF all three ext scenarios read content hashes from `GET /api/v1/extensions/catalog/{name}`, which no slice builds, and install by package name with nothing yet packing the example builds into the loopback index (`Loopback.serve_index` has no caller).
