Sources: six structured exploration reports (p2p, hexon, terrain, budget, camera, iroh). All citations are file:line as reported.

## A. STATE OF THE WORLD

**A1. How hexon bytes reach a peer today.** The only working large-asset transfer is a whole-file HTTPS GET: fe-hexon's `remote` feature downloads the entire `.hexon` archive in one `resp.bytes().await` from fe-hexon-registry (fe-hexon/src/remote.rs:96-106), whose `/download` route streams the file with Content-Length but no Range/Accept-Ranges support (fe-hexon-registry/src/routes.rs:256-275). The P2P path is aspirational: iroh 0.35 provides a bound QUIC endpoint with BBR (fe-sync/src/endpoint.rs:18-41) and outbound-only iroh-gossip JSON broadcasts (transforms, tileset advertisements — sync_thread.rs:557-571, 705-720), but no ALPN/protocol Router is registered anywhere, so inbound gossip and all P2P transfer are non-functional (fe-sync/src/AGENTS.md:55-57). iroh-docs replication is mock-backed (`IrohDocsEngineHolder::is_available()` always false → MockVerseReplicator, AGENTS.md:59-71, replicator.rs:105-139); iroh-blobs is pinned in workspace Cargo.toml:62 but consumed by no crate; fe-network's libp2p stack is a Kademlia-only swarm whose events are debug-logged (fe-network/src/lib.rs:55-57) with `fetch_asset` bailing "deferred to Sprint 5B" (iroh_blobs.rs:11-13). A complete chunked-tileset protocol (RequestTilesetMeta/RequestChunk/ChunkReceived, messages.rs:52-57,128-140; `package_chunked` size-capped chunk archives, fe-terrain/src/tiles/builder.rs:292-340; sequential UI driver, fe-ui/src/terrain_map/events.rs:110-175) exists end-to-end in types and wiring, but the sync-thread handlers are stubs emitting ChunkFailed (sync_thread.rs:727-759). The op-log/WAL path writes HLC-stamped rows (fe-database/src/op_log.rs:84-94), mirrors row JSON to a BLAKE3 content-addressed FsBlobStore, and forwards hash-only ReplicationEvents through two drop-on-full bounded(256) hops (fe-database/src/lib.rs:175-189; fractalengine/src/main.rs:123-137) into the mock replicator behind a currently-permissive fe-policy gate (write_policy.rs:17-23).

**A2. How tiles reach the GPU.** Two-tier: EAGER byte residency + LAZY mesh spawn. At app startup `registry.load_all()` loads EVERY installed tileset's full archive into RAM as `HashMap<String, Vec<u8>>` (main.rs:228; registry.rs:75-100; hexon_source.rs:37-59); on each petal assignment `apply_terrain_assignments` re-reads the whole `.hexon` from disk into a FRESH HexonTileSource — the active tileset is resident twice (petal_binding.rs:151; store.rs:216-224). Render-side, a per-frame system computes desired_zoom from camera real height (one step per doubling above 200 m, terrain_plugin.rs:184-195), walks a nearest-first radial ring capped by max_chunks=256 and the perspective far plane, and spawns ≤16 chunk meshes/frame via FULLY SYNCHRONOUS main-thread lookups (`CompositeTileSource::get_tile_sync`, composite.rs:165-243) — tolerable only because bytes are pre-resident. No async queue, no frustum test, no eviction for hexon data; the only eviction is a 512 MB disk cache for online-origin tiles whose LRU touch is a documented no-op (cache.rs:149-156). The async `fetch_tile` path exists behind the `fetch` feature but is never called by the renderer (composite.rs:255-334). Scale authority: TilesetMeta native_scale/gsd/scale_bounds (fe-format/src/manifest.rs:61-71), backfilled on load (store.rs:53-61), hexon overriding stored petal config (petal_binding.rs:165-192); GSD-aware `select_source_lods` is computed but NOT wired into the sync lookup (composite.rs:117-155).

**A3. Render-budget signals.** Five guardrail layers from commit 46e19de (the 2.76 GB create_bind_group crash: 8,192 glb stamps × embedded cameras → 16,387 extracted views → ~15.7M MeshUniform slots, spec.md:105-114): per-track MAX_STAMPS=4096 (path_asset_reconcile.rs:146), petal-wide MAX_STAMPS_PER_PETAL=65,536 with per-pass budget drawdown (path_asset_materialize.rs:190-198), MAX_PETAL_NODES=10,000 via cumulative `spawn_allowance` (spawn.rs:14-20, enforced at petal_respawn.rs:94-98, primitive_materialize.rs:151, db_results/hierarchy.rs:93), an app-wide Mesh3d watchdog with ceiling 2,000,000 running in Last whose `exceeded` flag zeroes every spawner's budget (fe-ui/src/plugin.rs:46-145, consumers at petal_respawn.rs:91 etc.), and `deactivate_foreign_cameras` in PostUpdate (fe-renderer/src/camera.rs:185-198). DIAG-15M logs per-frame render census (RenderMeshInstances, ExtractedView count, GPU buffer bytes, HOT-view flag >100k work items) at debug level only (fe-runtime/src/diag15m.rs:31-123). FR-6 "render horizon" (camera-radius materialization + hysteresis streaming) is fully specced but ZERO code exists (plan.md:39-43 all unchecked; grep for render_horizon/hysteresis: no hits); the only distance knob is the unconsumed `PetalManifest.render_distance` default 500.0 (terrain_map/manifest.rs:14-25). Key structural blindness: the watchdog counts Mesh3d entities but views (cameras × shadow lights) were the crash multiplier, and Bevy render buffers never shrink after a spike (spec.md:112-115).

**A4. Camera stack.** A single Blender-style orbit controller in fe-renderer/src/camera.rs: Camera3d spawned at Startup with OrbitCameraController {focus, distance=8.66, yaw, pitch}, near=0.01, driven by `orbit_camera_system` (middle-mouse orbit, shift+middle pan, proportional log zoom, WASD/QE fly) (camera.rs:64-84, 221-242, 248-383). Zoom-OUT limit and far plane ARE scale-aware via CameraScaleSettings (`scaled_max_distance = clamp(BASE/world_scale, 500..100_000)`, camera.rs:137-149) fed each frame from the active petal's TilesetMeta world scale (fe-ui/src/terrain_map/mod.rs:93-102); min_distance=0.05 and near are fixed. There is NO ground/terrain collision or min-height clamp anywhere — focus and camera go arbitrarily below terrain (camera.rs:154-166, 360-362). No cheap height-at-(x,z) exists: elevation grids are consumed into meshes and dropped (terrain_plugin.rs:435-457; TerrainChunk stores only tile_coords+lod, :77-82); the sole point sample is a blocking tile-fetch+PNG-decode mean (petal_binding.rs:251-275). No smoothing/lerp/damping utilities exist anywhere in the workspace (grep: zero matches). Single-camera invariant is load-bearing: `query.single_mut()` and multiple fe-ui `.single()` queries break silently with a second camera (camera.rs:274; router.rs:128; gimbal_interaction.rs:24,153).

## B. DECISION POINTS

### D-A: P2P transfer granularity

| Option | Pros | Cons |
|---|---|---|
| **A1. Whole-hexon blob** (status quo shape, over iroh-blobs instead of HTTP) | Simplest; matches existing all-in-memory import paths (`HexonArchive::import` archive.rs:255-449, `HexonPackage::open` package.rs:149-277); one hash to announce | 10GB-class tilesets forced fully resident before use; registry publish already caps at 1 GiB "tilesets are large" (routes.rs:21-22); defeats streaming entirely; 0.35 can't range-split one blob across peers (iroh report, downloader docs) |
| **A2. Per-tile blobs via HashSeq collection** (manifest blob = tile index + TilesetMeta; one child blob per tile/tile-bundle) | Works FULLY on iroh 0.35 today: single GetRequest fetches manifest + arbitrary child subset (0.35 protocol docs); per-tile dedup across hexon versions for free; sidesteps 0.35's weak random-access partial-blob tracking (DESIGN.md: missing ranges recomputed assuming mostly-sequential writes); iroh-blobs fs store explicitly designed for millions of small blobs (inlines ≤16 KiB into redb) | Per-child metadata cost (32 B HashSeq entry + DB row); raw tiles are often <16 KiB (outboard-less, DB-dominated) unless bundled; diverges from the existing chunk protocol vocabulary |
| **A3. bao ranged reads into ONE blob, PMTiles-style layout** (Hilbert-ordered tiles + directory, fetch via ChunkRanges) | Fewest blobs/metadata; spatially-adjacent tiles coalesce into contiguous 16 KiB-aligned ranges; tiles are already Stored (uncompressed) in the zip so byte-range equivalence holds (archive.rs:209-213); proven prior art (PMTiles v3) | On 0.35, random-access partials into one giant blob degrade resume tracking (DESIGN.md); the 0.35 ranged-request surface (RangeSpec/RangeSpecSeq) goes private in 0.90+ — code written against it must be re-expressed; requires new archive layout (Hilbert ordering, directory) |
| **A4. Hybrid: HashSeq of tile-BUNDLES sized 16 KiB–tens of MB** (e.g. per-zoom-level or per-spatial-cell chunk archives — reusing `package_chunked`/ChunkIndex, builder.rs:292-340, manifest.rs:104-113) | Reuses the existing chunked pipeline end-to-end (messages.rs:52-57, events.rs:110-175, distribution.rs:311-333 — only the sync_thread.rs:727-759 stubs need real bodies); bundle sizing follows DESIGN.md economics (above 16 KiB, below tens of MB); stable across the 0.35→1.0 break (hash + HashSeq semantics survive); coarse-LOD-first ordering gives progressive rendering | Coarser than per-tile fetch (over-fetch within a bundle); ChunkIndex needs a per-chunk blake3 added (currently absent, messages.rs:128-134) |

**Recommended default: A4** — HashSeq of size-tuned chunk bundles, with A2 (per-tile) as the refinement for hot zoom levels if over-fetch proves painful. Rationale: it is the only option that (a) reuses the fully-wired existing protocol scaffolding, (b) works on 0.35 semantics today, and (c) survives the 0.90+ API rewrite because it never touches RangeSpec directly. Adopt PMTiles-style spatial ordering WITHIN bundles so a later move to A3 on 1.0 blobs is a layout change, not a redesign.

### D-B: Streaming engine shape (scene-driven residency)

**What drives prefetch:**
| Option | Pros | Cons |
|---|---|---|
| **B1. Radial render-distance rings** (extend existing lod_ring.rs; PetalManifest.render_distance as knob) | Ring math already exists, pure and tested (lod_ring.rs; terrain_plugin.rs:313-332); config knob already persisted and user-editable (manifest.rs:14-25, dialogs/petal_manifest.rs:53-59); matches FR-6 spec (spec.md:77-84) | No direction awareness — fetches behind the camera |
| **B2. Frustum + camera-forward weighting on top of rings** | Camera forward vector extension to `ring_offsets`/`view_radius_world` is pure and unit-testable (camera report, terrain opportunities); halves wasted prefetch | More math; hysteresis needed so rotation doesn't thrash the want-list |
| **B3. Closed-loop GPU-budget-driven horizon** (shrink radius when DIAG-15M's data_buffer bytes approach a limit) | Ground-truth signal already queried per-frame (diag15m.rs:59-122); directly prevents the never-shrinking-buffer failure mode (spec.md:114-115) | DIAG-15M is explicitly a temporary debug scaffold (diag15m.rs:1) — must be promoted to a shared resource first |

**Where it lives:** (i) inside fe-terrain's scheduler — colocated with the only tile consumer, but conflates tile-byte residency with node/stamp residency; (ii) a new first system in fe-ui's chained VerseManagerPlugin group (verse_manager/mod.rs:154-166) — the single choke point for ALL node/primitive/stamp spawning, where every spawner already accepts a budget (`spawn_allowance`, `take_stamp_budget` are pure + tested); (iii) a new fe-streaming crate — clean but premature given fe-ui-must-not-depend-on-fe-terrain boundary (terrain_map/mod.rs:107) forces awkward plumbing either way.

**Eviction:** despawn-on-exit-ring with hysteresis (×1.5 despawn radius already the pattern, terrain_plugin.rs:212-270); byte-level eviction via Arc'd TilesetRegistry sources + petal-scoped drop (registry.rs opportunities); keep count caps as the safety net underneath (spec.md:84).

**Recommended default:** B1+B2 combined, computed as a "residency ledger" resource written before `respawn_on_petal_change` in the VerseManagerPlugin chain (option ii), replacing the boolean `mesh_budget.exceeded` gate with a distance-ranked allowance; extend MeshInstanceBudget (plugin.rs:51-75) rather than adding a parallel resource. Tile-byte streaming stays in fe-terrain (lazy HexonTileSource offset-index + AsyncComputeTaskPool dispatch of the already-existing `fetch_tile` seam, composite.rs:255-334); node/stamp streaming lives in fe-ui. B3 is phase 2, gated on promoting DIAG-15M census to a resource. Critical constraint: prevention not recovery — the horizon must gate spawns BEFORE the spike because render buffers never shrink (spec.md:114-115); hysteresis is mandatory (stamp groups already churn-respawn every 30-60s, spec.md:124). Prior-art specs `_archive/render_distance_lod_20260407` (3-tier LOD, 1000 m hard limit) and `_archive/relay_data_horizon_20260407` must be read first (mandated, plan.md:41).

### D-C: Registry/HTTP parity — Range support in RemoteRegistryClient

| Option | Pros | Cons |
|---|---|---|
| **C1. Add member-granular routes** (`GET /{uri}/tiles/{z}/{x}/{y}` or generic `/{uri}/file/{path}`) | 90% present: `read_zip_bytes` already serves single members lazily (index.rs:32-43) and the per-entry asset route exists unused (routes.rs:210-254); client just needs methods beside `download()` (remote.rs:96-107); granularity matches the P2P want-list (tile/chunk ids) | Server does zip resolution per request; new API surface to version |
| **C2. Add Accept-Ranges/Range to /download** | Tiles are Stored so byte-ranges are byte-identical to standalone files (archive.rs:209-213); client range-reads via ZIP central directory with zero server-side zip logic; standard HTTP semantics, CDN-cacheable | Client must implement EOCD parsing; JSON members are Deflated so ranges of them are useless (archive.rs constraint); byte-range granularity ≠ P2P chunk granularity — two partial-fetch abstractions |
| **C3. No parity — keep hosted path whole-file** | Zero work; registry stays simple | The 1 GiB publish cap already strains (routes.rs:21-22); hosted users get none of the streaming benefit; two divergent client code paths forever |

**Recommended default: C1**, unified behind a single trait — a `PartialHexonFetch` abstraction (fetch manifest/meta; fetch named member or chunk by id) with an HTTP impl (new routes) and an iroh impl (D-A bundles). This makes fe-hexon's transport-agnostic FetchStrategy (semaphore, peer priority, sig verify — fetch.rs:39-129) the shared policy layer over both. C2 can be added later as a cheap bonus for third-party tooling. Keep client changes behind the `remote` feature gate (fe-hexon/Cargo.toml:10-11). Also: streaming client import must split `HexonArchive::import` into header phase (manifest+entries+tileset_meta — exactly what `index_one` does, index.rs:46-73) + on-demand member reads; TilesetMeta is already available without tile bytes via `{id}.meta.json` (store.rs:12,148-152), satisfying the metadata-before-bytes constraint (petal_binding.rs:153-192).

### D-D: Integrity granularity for partial fetch

Current state: Ed25519 covers the manifest JSON ONLY (two mutually incompatible schemes: fe-format canonical-JSON, signature.rs:53-94, vs fe-hexon raw-bytes signature.txt, fe-hexon/src/signature.rs:9-34). Per-asset blake3 hashes exist in entries.json but are NEVER verified against blob bytes on install (registry.rs:157-178) or publish (routes.rs:294-328); tiles are covered by neither signature nor hash (excluded from entries.json by design, archive.rs:219-222); ChunkReceived carries no per-chunk hash (messages.rs:128-134); registry publish accepts unsigned packages (routes.rs:310-328).

| Option | Pros | Cons |
|---|---|---|
| **D1. Trust bao only** (iroh transport verifies every 16 KiB against the requested hash) | Zero format work; per-16KiB detection is strong (0.35 protocol docs) | bao verifies bytes-match-hash, not hash-is-authorized: nothing binds the tile/chunk hashes to the PUBLISHER's signature. An announcement carries only manifest_hash with no binding to archive bytes (announce.rs:12-30 constraint); a malicious peer can serve a validly-bao-verified blob for a hash it chose. Also does nothing for the HTTP path (C1). |
| **D2. Merkle-extend the signature root** — signed manifest commits to entries.json digest + tile/chunk index digest (per-chunk blake3 in ChunkIndex); enforce asset_hash verification at FsBlobStore.store/install and registry routes | Extends the existing Ed25519 root of trust to full-package coverage; `asset_hash()` helper exists (signature.rs:43-46); transport-agnostic — same trust chain over HTTP and iroh; `verify_fetched_manifest` already gates before blob transfer (fetch.rs:105-129) | Format change (manifest field additions); must not break existing unsigned test fixtures (routes.rs constraint); requires resolving the two-signature-scheme split |
| **D3. D2 + per-chunk signatures** | Chunk-level non-repudiation | Overkill: a hash committed under one signed manifest is equivalent trust with far less key traffic |

**Recommended default: D2.** bao remains the transport-layer verification; the signed manifest becomes the authorization root that commits to every fetchable unit's hash. Sequence: (1) add per-chunk blake3 to ChunkIndex/TilesetMetaReceived; (2) commit entries.json digest + chunk-index digest into the signed manifest; (3) enforce asset_hash on install and registry publish (verify signature at publish too). Prerequisite decision: collapse the two format stacks — recommend fe-format v1.0.0 canonical-JSON as the survivor, with a compat verifier for legacy signature.txt packages (the P2P announce/fetch code is currently built on the LEGACY manifest, announce.rs:86 — must migrate).

### D-E: iroh upgrade timing vs relay EOL 2026-12-31

Facts: 0.35 public relays hard-EOL Dec 31 2026 (~5.5 months out); the relay wire protocol broke in 0.91 (ECN byte) so there is no gradual interop — the whole stack jumps together (iroh report). 0.90+ blobs is NOT yet labeled production-quality; 0.35 is n0's recommended production version today. The blobs API break is a rewrite (RangeSpec→ChunkRanges, irpc, snafu) but on-disk store format AND request semantics (hash + chunk ranges + HashSeq) are forward-compatible. Repo reality: iroh-blobs is pinned but wired to nothing (Cargo.toml:62; fe-network/src/iroh_blobs.rs:4-13 stub; blob_store.rs:6-8 deliberate non-adoption) — streaming is greenfield, there is no legacy transfer code to preserve. fe-sync also pins iroh-quinn-proto 0.13 in lockstep for BbrConfig (AGENTS.md:11-19). Relay failure mode today is QUIET: default n0 relay binding with no relay_url config wired (endpoint.rs:33-41; fe-network IrohConfig.relay_url is dead code), offline detection only checks bind failure (sync_thread.rs:58-73) — post-EOL, gossip silently queues forever.

| Option | Pros | Cons |
|---|---|---|
| **E1. Block streaming on the 1.0 upgrade** | Write ranged/multi-provider code once against final APIs; get SplitStrategy/Observe/GetMany immediately | Streaming stalls ~months on a not-yet-production dependency; upgrade risk and streaming risk compound in one track |
| **E2. Build on 0.35 behind a transport trait** (design to hash+ranges+HashSeq semantics; keep RangeSpec types out of public seams) | Ships now on the production-recommended version; the D-A/A4 design deliberately uses only concepts stable across the break; the migration then buys bitfield resume + swarm download without redesign; on-disk store carries over | Some 0.35-specific glue is throwaway; single-provider throughput per blob until 1.0 |
| **E3. Build on 0.35 raw, migrate ad hoc** | Fastest first demo | RangeSpec surface goes private in 0.90+ — guaranteed rewrite of exactly the code that matters |

**Recommended default: E2**, plus an immediate independent hardening item regardless of choice: wire RelayConfig (RelayMode::Custom/Disabled) into `SyncEndpoint::new` and surface relay health in SyncStatus (status.rs:20-28) so the EOL fails loudly; the repo already has the docker relay-container pattern for self-hosting. Schedule the 1.0 jump as its own track (iroh_1_0_upgrade_20260711 exists) with a hard internal deadline well before 2026-12-31, and bump iroh-quinn-proto in lockstep. fe-hexon-registry is the designated ContentDiscovery provider (hash → node ids) for the 1.0-era downloader.

## C. CAMERA HARDENING PLAN

**1. Terrain height provider (prerequisite for the clamp).**
- `fe-terrain/src/terrain_plugin.rs` — in `spawn_chunk` (:385-457), the final scaled elevation grid (grid/gw/gh at :438-440) is in hand right before `terrain_mesh` consumes it; insert it into a new `TerrainHeightField` resource (`HashMap<tile_coords, HeightField{grid, dims, tile_world_size}>` keyed like TerrainChunk.tile_coords) at zero extra decode cost. Remove entries on chunk despawn (`update_terrain_lod`, :212-270) and clear on assignment revision bump (:301-304).
- API: `height_at(x, z) -> Option<f32>` via O(1) bilinear sample, world units (grid is already `(ele − origin_ele) × scale`, petal_binding.rs:202-213, scale.rs:31-45 — no further scaling needed).
- Crate boundary: fe-ui must not depend on fe-terrain (terrain_map/mod.rs:107). The clamp therefore lives in fe-renderer reading a renderer-visible resource that fe-terrain writes — follow the proven CameraScaleSettings channel pattern (fe-ui/src/terrain_map/mod.rs:93-102; Option<Res> defensive, headless-safe). Concretely: define a small `TerrainHeightProvider` resource type in fe-renderer (or fe-runtime), populated by fe-terrain's render feature.
- Explicitly rejected alternatives: `sample_center_elevation`-style sync fetch+decode is blocking and ms-scale (petal_binding.rs:251-275, get_tile_sync unsuitable per-frame per :260); Assets<Mesh> vertex readback hits the VertexAttributeValues access gotcha (project memory); MeshRayCast per-frame is deliberately avoided (fe-ui/src/node_manager/AGENTS.md:191-198).

**2. Min-height/terrain clamp.**
- `fe-renderer/src/camera.rs` — single choke point at the end of `orbit_camera_system` (:377-382) where `*transform` is recomputed: add pure fn `clamp_camera_above_ground(transform_y, focus_y, ground_height, margin) -> (f32, f32)` clamping both `transform.translation.y` and `controller.focus.y` against `height_at(x,z) + margin`. Also clamp inside `apply_pan` (:154-166) and the WASD/Q/Ctrl vertical moves (:332-374, esp. :360-362 unbounded focus descent). Margin must be world-scale-aware (multiply by CameraScaleSettings.world_scale). Fall back to no clamp when the provider has no data (petal without terrain; origin grounding only holds after `sample_center_elevation` succeeded, petal_binding.rs:205-213). For flat/no-terrain petals, optionally clamp to `ray_plane_y`-style y=0 floor (helper exists, path_point_interaction.rs:199).
- Follow the pure-fn + unit-test pattern of camera.rs:389-593; new defaults must not break pinned tests (e.g. `default_min_distance_allows_close_zoom_without_clipping`, camera.rs:587-592).

**3. Scale-aware zoom-in defaults keyed to TilesetMeta.**
- `fe-renderer/src/camera.rs` — add `scaled_min_distance` mirroring `scaled_max_distance` (:137-144) and apply it in `apply_camera_scale` (:202-218). Do NOT touch near=0.01 (deliberately tuned, camera_focus_clip_20260716 FR-3; apply_camera_scale intentionally never touches near, :235-236). Zoom step fraction (ZOOM_FRACTION=0.1, :124-133) can stay scale-free since it is proportional to distance already.
- No fe-ui change needed: CameraScaleSettings is already written per-frame from petal TilesetMeta (terrain_map/mod.rs:93-102); clamp `controller.distance` into the new [scaled_min, scaled_max] on scale change (extend :213).

**4. Damping/easing (new — nothing exists, grep: zero lerp/smooth matches).**
- `fe-renderer/src/camera.rs` — add `target_distance: f32`, `target_focus: Vec3` to OrbitCameraController (:64-84); inputs write targets; `orbit_camera_system` applies frame-rate-independent exponential decay `current += (target − current) × (1 − exp(−rate·dt))` before the final `compute_orbit_transform` (Time already a system param, :255,333). Pure decay fn + tests. Keep WASD dt-scaling (:333-334), the S-key first-press skip (:348), and the exact egui `is_using_pointer` gating incl. event draining (:258-272) untouched.
- Bonus seam: target_distance/velocity feeds tile prefetch along the zoom trajectory (terrain_plugin.rs:322-337, lod_ring.rs:21,123).

**5. Foreign-camera hardening (from budget report follow-ups).**
- `fe-renderer/src/camera.rs` — `deactivate_foreign_cameras` (:185-198) is one-shot via Added<Camera>: insert a `ForeignCameraDisabled` marker at deactivation + periodic sweep over `is_active` to catch late re-activation; generalize to strip shadow-enabled punctual lights from foreign scenes (stated follow-up, spec.md:122-123). Marker doubles as explicit exemption mechanism for future legitimate second cameras — which currently break `.single()` silently (camera.rs:274; router.rs:128; gimbal_interaction.rs:24,153).

**Files to touch (exhaustive):** `fe-renderer/src/camera.rs` (clamp, scaled_min_distance, easing, foreign-camera marker, tests); `fe-terrain/src/terrain_plugin.rs` (HeightField insertion at spawn_chunk, removal at despawn/revision); a new small module for the HeightField resource type in `fe-renderer` or `fe-runtime` (boundary-dependent); `fe-terrain/src/lod_ring.rs` only if prefetch-along-trajectory is taken now. No fe-ui changes required.

## D. RISKS & UNKNOWNS

1. **Quiet relay death (highest urgency).** Post-EOL 2026-12-31, iroh nodes bind fine, node_addr relay discovery degrades, gossip queues silently forever — offline detection only checks bind failure (sync_thread.rs:58-73); no relay_url config is wired anywhere (endpoint.rs:33-41; fe-network types.rs:14-23 dead code). Decision round must ratify self-hosted relay vs 1.0-upgrade deadline. Note fractalengine-relay is the app's headless server, NOT an iroh relay.
2. **Two parallel P2P stacks with disjoint identity.** libp2p/fe-network (fresh throwaway keypair each start, lib.rs:20) vs iroh/fe-sync (deterministic NodeId from fe-identity, main.rs:59). fe-hexon's p2p module targets the never-built libp2p Kademlia path (p2p/mod.rs:3-5). Consolidation decision (kill fe-network's DHT role? D-71 said keep P2P/fe-network) must precede D-A implementation.
3. **Two divergent hexon format stacks + incompatible signature schemes.** fe-format v1.0.0 vs fe-hexon legacy crate manifest; P2P announce/fetch is built on the LEGACY one (announce.rs:86, package.rs:4). D-D's Merkle extension forces the unification decision; re-serialization breaks raw-bytes signatures (registry.rs:141-142).
4. **Render buffers never shrink — prevention-only budget.** One spiked frame permanently poisons BatchedInstanceBuffers (spec.md:114-115). Any streaming bug that momentarily over-spawns is unrecoverable in-process. The Mesh3d watchdog is structurally blind to view fan-out (cameras × shadow lights, spec.md:112-113,122-123) — glb-embedded shadow lights could recreate the crash TODAY.
5. **Double-residency memory math.** Active tileset resident twice (registry load_all + fresh per-assignment load, petal_binding.rs:151 vs registry.rs:75-100); any memory budget is off by 2× until deduplicated (Arc<HexonTileSource> change).
