## Pinned API compatibility and one native response

The new `ui_shell/icons.rs` uses an actual public egui0.33.3 path:

- `Atom::custom(id,size)` is public (`src/atomics/atom.rs:57–63`) and stores fixed size plus Custom ID. `Atoms::new` accepts IntoAtoms and `push_right` accepts Into<Atom> (`atoms.rs:15–24`). The blanket Atom/AtomKind/IntoAtoms conversions support owned WidgetText and the composed Atoms. A Button<'static> can own these values; no borrowed text lifetime or invented custom-widget API is needed.
- Public `Button::new` accepts IntoAtoms and initializes native click sense/font fallback (`widgets/button.rs:44–61`). Public `atom_ui` (`:253–350`) performs the native minimum/frame/layout/interaction/WidgetInfo path; ordinary Widget::ui simply returns its response. IconButton calls that path once and returns **the same response**, without creating a second interact region, child UI or explicit widget ID.
- `AtomLayoutResponse::rect` is a public optional lookup (`atom_layout.rs:451–480`). Custom rectangles are local entries in that returned layout (`:436–441`); reusing a constant icon-slot ID across different buttons cannot merge their native widget identities. The candidate handles absent custom rects without unwrapping, matching the SDK's invisible-widget contract.
- Native text remains a Text atom. For truncating property previews, AtomLayout marks the text atom as shrink and gives it remaining width after fixed atoms (`atom_layout.rs:173–270`); the icon slot does not consume or rewrite the stored value. Ordinary native text layout/WidgetInfo remains responsible for captions.

No implementation parser/compiler was invoked. These are source-proven method/type contracts, not a successful typecheck claim.

## IDs, names, roles, disabled and selected behavior

Callers retain explicit `.named`/hover names and existing enable predicates. Native Button assigns its own response and Button role; custom atoms add no action/ID owner. A textless native button may initially have an empty native caption, then the unchanged caller's ResponseExt names it. This remains the established explicit-name path rather than requiring an icon character to stand in for an accessible name.

The adapter default minimum uses the same layout_policy::target_size. Call sites that previously used layout_policy::action now call ui.add(...).named with that identical adapter minimum; the old helper itself only applied that minimum and named the response (`layout_policy.rs:1150–1153`). The explicit min_size/fill/frame/truncate builder methods delegate directly to the same Button.

Native disabled behavior remains in `ui.add_enabled`/add_enabled_ui. Pinned `ui.rs:1848–1858` disables the original UI/painter while drawing and restores it afterward. The adapter paints while that disabled painter is active; Painter::with_clip_rect clones the painter, retaining opacity (`painter.rs:71–74`). It does not paint an enabled overlay over a disabled control or implement a second click handler. Default icon tint uses native interaction text color; explicit tree tint remains explicit and receives painter opacity.

Existing active tool/rail fills remain in their callers. No new semantic selected flag or selection mutation is introduced. Thus the candidate preserves the existing selected convention rather than claiming the native role now exposes a new selected state. Caption focus/hover frames remain native, while icon line color follows the same current interaction visuals. Root must still inspect focused/hovered/disabled appearance after rebuilding.

## Geometry, clipping and intrinsic width

The reserved icon extent follows the resolved native Button font size, capped14 logical points; paint uses that returned custom rectangle. Line art uses1.25-point strokes with an inset, or the existing TreeIcon Circle/Ring/Square painter. Reviewed all21 variant branches: fixed geometry depends only on the enum/rectangle/color, with no user data, external font, texture, path, IO or callback. Filled disclosure triangles use bounded convex polygons; visibility states select existing filled/ring/mixed semantics.

The icon painter intersects caller clip with the native response rect. Existing TreeIcon primitives also fit the reserved14-point rectangle: its ring radius subtracts the stroke allowance. The adapter never expands the control's hit region to match paint. The target minimum remains independent of the smaller visual symbol, so thin icons do not reduce physical interaction targets. Painter clipping also prevents this fixed symbol from escaping its native control during scroll/partial visibility; it does not imply a partly clipped control has passed whole-target acceptance.

Toolstrip allocation still comes from native Button atom layout: fixed custom width plus native icon_spacing/text/frame margins, with the existing responsive topbar/menu policy. It is **not guaranteed pixel-identical** to a Unicode glyph plus space. The fixed1160-point compact threshold is unchanged. Accordingly actual1280/1x and both sides of the current responsive threshold, with Deselect present and all right-hand controls visible, are required rebuilt checks. No current frozen screenshot can prove the revised strip fits. This practical risk is explicitly retained in the author report and is an execution requirement, not a speculative source defect or permission to waive clipping.

No direct-painter payload contains user text; optional captions remain ordinary native text. Paint is confined to the already-owned control/caller surfaces. No extra floating area, capture producer registration, privacy classification or positive capture capability is introduced. Capture acceptance itself is outside this source verdict.
