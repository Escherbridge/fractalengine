# Require-existing: supported maintenance contract feasibility

Source-only feasibility, 2026-11-04. **No complete supported ordinary-client recipe is established. Retained roots remain HOLD.** Allowing the locked SDK's narrowly identified cluster maintenance before owner admission is a concrete possible deviation from the approved design; it does not by itself eliminate the remaining unsafe-open mechanisms. The strongest new blocker is not a hypothetical physical write: ordinary client startup also enables queued async events that can write application records before owner admission. Automatic corrupt-WAL repair is another concrete mismatch.

Read the approved `.omc/research/require-existing-startup-design-v1.md` and isolated partial spike report, then followed only their named locked startup seams and the newly reached task/event paths. The strict design remains the selected design. This report proposes no automatic waiver, source integration or retained opening. It does not conclude that every possible supported API was exhausted, or that a permanent three-crate fork is inevitable.

## Three mechanisms that prevent a grounded no-fork recipe today

**1. Async events can cross the hard no-application-write boundary.** `engine/tasks.rs:230–263` periodically invokes `Datastore::event_processing`; core `kvs/ds.rs:1666–1693` acquires a task lease and processes queued batches. `doc/event.rs:267–301` restores persisted namespace/database, permissions and auth; `:404–468` creates writable transactions, runs the stored event and commits, or updates/deletes its queue on failure. `:175–187,520–535` evaluates the stored THEN expressions. This can update app records using persisted authority independently of host Seed/reconciliation.

The actual public SDK Config (`opt/config.rs:13–33,116–143`) offers four membership/changefeed interval setters, **no event/index-task disable or start-after-admission control** in this named path. Passing None or zero to those setters falls back to normal defaults; it does not disable them. A large interval is not an ownership barrier, and the owner query cannot be assumed to finish before5s. `Capabilities::none` is useful for closing network/functions/script surfaces but is not a blanket transaction-write prohibition for stored plain statement expressions. No queue-empty proof exists before the engine has opened; the absence of ASYNC definitions in current application authoring would not prove a retained engine's queued contents absent. This report does not claim an actual retained queue exists. The counterexample means ordinary startup is not generally confined to internal maintenance.

**2. The adapter selects corruption repair without a supported override in the inspected configuration.** SurrealKV `lib.rs:145–154,257` defaults to `TolerateCorruptedWithRepair`. `lsm.rs:1096–1152` repairs a corrupt WAL segment and retries; `AbsoluteConsistency` instead fails without repair. The core adapter `kvs/surrealkv/mod.rs:50–88` constructs TreeBuilder but never selects recovery mode, and the named SurrealKvConfig/adapter environment knobs do not expose one. The underlying KV public builder has `with_wal_recovery_mode` (`lib.rs:469`); that is **not** an option propagated through the installed ordinary Surreal client. Calling it on a separate Tree would be a forbidden second/raw opener, not a solution. A weaker decision that permits cluster metadata does not permit corrupt history truncation/repair silently.

**3. File pins have a real lifecycle compatibility obligation.** Requiring the existing root and `manifest/00000000000000000000.manifest`, with nonreparse pinned ancestors and stable existing key leaves, is useful and may remove a large class of replacement-store races. It is not a proof by itself. SDK LevelManifest checks path existence then reads it (`levels/mod.rs:146–205`); there is no public callback acknowledging its loaded identity. A manifest handle denying deletion held through opening would also oppose legitimate manifest replacement: `replace_file_content` writes/syncs a temporary file then renames over the manifest (`:576–616`), including recovery flush paths. Releasing the pin at an arbitrary delay or only after ordinary connection success leaves either a startup conflict or an unproved handoff. Directory pins bind ancestors, not a child manifest's content, and denying deletion alone permits writes through compatible handles. A cooperating app lifecycle lock is necessary but does not prove the SDK opened the exact pinned child. The existing SDK lock's create/truncate-before-exclusive behavior also remains (`lockfile.rs:69–95`). These are concrete design/execution questions; no OS behavior was tested here and no universal claim about every possible Windows guarding strategy is made.

## Bounded contract proposal and decision

A reviewable weaker contract could say:

> After load-only real-key admission and protected existing physical-store admission, permit only the SDK's version/membership/live-query bookkeeping and valid confined engine recovery before the application reads its actual retained Verse owner/schema. On a later owner/schema refusal, those disclosed internal changes may remain. Never create a replacement catalog or application namespace/schema/owner/history/role/blob record, run queued application events, repair corrupt WAL, generate/heal secrets, reconcile/Seed, expose a shared handle or start app services before acceptance.

This is an **explicit deviation** from the approved ordering that defers all SDK logical bootstrap. It is a decision proposal, not accepted equivalence. Allowing version creation also weakens the approved refusal on absent version metadata; if absent-version initialization is excluded, an existing-version read seam remains required. Membership cleanup can remove expired live subscriptions; the acceptance record must say so rather than promise all SDK logical keys remain unchanged.

No current supported ordinary-client recipe is proposed as satisfying that text: the three mechanisms above are not closed. A candidate that simply pins files, calls `Surreal::new::<SurrealKv>`, calls use_ns/use_db, then checks created_by is specifically insufficient. Omitting app DDL would improve the host sequence but leave both event writes and recovery repair possible. An SQL string `BEGIN TRANSACTION READONLY` is not a discovered solution: the locked parser's `syn/parser/stmt/mod.rs:277–281` consumes optional TRANSACTION only and offers no such read-only begin mode. Do not invent a client read-only API from a low-level transaction facility.

The smallest next engineering decision is therefore whether to retain the strict design, or independently approve only the narrower internal-maintenance allowance above and then implement the still-missing **startup task gate, fail-closed recovery propagation and proven physical handoff**. The latter could reduce the need for a pre-bootstrap owner callback and can reuse ordinary cluster methods; it still requires actual reviewed SDK support or a narrowly pinned change. It does not establish that the whole existing spike or three-crate fork is necessary, and no dependency change is authorized here. Replacing all existing Surreal shared-handle consumers with a custom core/router is not a bounded supported-client recipe.

Once those mechanisms exist, the host can own one connection privately, validate existing namespace/database/schema and exactly the retained Verse against the actual loaded DID with read-only execution, recover clocks with checked errors, and only then publish readiness. `use_ns/use_db` must be reached only after a source-proven existing-scope boundary, not used to establish existence. Keep all approved no-Seed/queued-Seed, no-reconcile/migration/role/blob initialization, delayed API/network/token and legacy/pair provenance requirements. Public informational/SELECT syntax alone is not a substitute for the missing physical and task boundaries.

Acceptance remains disposable first: missing/replaced catalog; version/owner/schema mismatch; wrong key; corrupt WAL; pending async event that would mutate a sentinel app row; interrupted admission; contention; and valid recovery requiring manifest replacement. Every failed admission must prove no app records/history/blob/identity changes and no external readiness, while separately recording allowed internal maintenance. Positive cases must prove the same real owner, continuously owned same store, preserved logical baselines/history and post-resume edit/replay. No offline opener, DB copy, raw KV forensic substitution or fake DID is permitted. Retained stores stay HOLD until implementation and independent source/runtime acceptance, not merely contract discussion.
