# Specification: Revive the dormant plugin host

**Track ID:** `plugin_host_revival_20261031` · **Type:** feature · **Priority:** P2
**Crates:** `fe-plugin` (host, sandbox, lifecycle, capability tokens), `fe-sdk` (stable extension API), `fe-ui` (consent UX, UI slot registry), `fe-api` (extension routes), `fractalengine` + `fractalengine-relay` (host thread spawn), `extensions/iot-bridge` (example)
**Citations computed at:** `f55ca21`. Symbol names are stable. Line numbers are not, so re-grep before editing.

## 1. User vision (2026-10-31, open-core alignment)

This track delivers the **open** plugin capability that any plugin catalogue — anyone's — would need to build on. Per the ratified open-core rule (`conductor/open-core.md`): *anything a self-hoster needs to run, verify, or extend FractalEngine is open and lives here.* A working plugin host, a verifiable package format, and an install path are exactly that. Review pipelines, counter-signing authorities and revocation-list publishers are operated outside this repository by whoever chooses to run them; this repo defines the seam (S-PLUGIN) and never imports, names, or feature-flags any of them.

## 2. Problem & evidence: complete engineering, zero wiring

Phase 9A-9C (`AGENTS.md` §Plugin System) shipped a real plugin system — 89 tests, three review passes. It has had no dependents since. Verified 2026-10-31:

- **No crate depends on `fe-plugin`.** `git grep -rn "fe_plugin::\|PluginHostPlugin"` outside `fe-plugin/src/lib.rs` itself returns nothing. Neither `fractalengine/Cargo.toml` nor `fractalengine-relay/Cargo.toml` lists `fe-plugin` as a dependency, and neither spawns a 7th thread for it despite `fe-plugin/src/lib.rs:1` documenting "thread 7" and `AGENTS.md` §architecture describing the crossbeam bridge in full.
- **The first-party extension doesn't even self-register.** `fe-terrain/src/extension.rs::register_terrain_ui` (`:44`) and `fe-terrain/src/api_ext.rs::terrain_api_routes` (`:13`) exist, are unit-tested, and are never called anywhere outside their own test modules — verified by `grep -rn "register_terrain_ui\|terrain_api_routes"` across the workspace. Nothing populates a `UiExtensionRegistry`: `grep -rn "UiExtensionRegistry\|PluginRegistry" fe-ui/src fractalengine/src fractalengine-relay/src` returns zero hits. The "Terrain Config" inspector section and "GPX Import" sidebar tool described in `extension.rs`'s own doc comment do not exist in the running app.
- **`ApiExtensionHandle` has no consumer.** `fe-sdk/src/api.rs:4-5` documents "the engine merges these into the main axum router under a namespaced prefix" — but `fe-api` does not depend on the pattern at all: only `fe-sdk/src/api.rs`, `fe-sdk/src/lib.rs`, and `fe-terrain/src/api_ext.rs` reference `ApiExtensionHandle` in the entire workspace. `fe-terrain/src/api_ext.rs:13-21`'s two declared routes (`GET /elevation-profile/:track_id`, `GET /stats/:track_id`) are not reachable through the real `fe-api` HTTP server.
- **"Signature verification" is a hash self-check, not authentication.** `lifecycle.rs::install_plugin` (`:73-89`) compares a BLAKE3 hash of the bytes against a caller-supplied `expected_hash` — the caller controls both sides of the comparison, so this authenticates nothing about *who* published the plugin. `AGENTS.md` §lifecycle already says this plainly: "'Signature verification' at install is a BLAKE3 hash check ... (absent = skip)." SECURITY.md's "plugin sandbox is young" line and the deny.toml wasmtime advisory block (19 RUSTSEC ignores, `deny.toml:79-97`, each reasoned "fe-plugin WASM host dormant") both key off the same fact: the attack surface is inert *only because nothing runs it*. Reviving the host makes every one of those ignores live.
- **A capability the manifest declares is never checked.** `CapabilityManifest`/`CapabilityToken` carry `network_scope: String` and `external_http: bool` (`capability.rs:34-39`, `:73-76`). The only code that reads `external_http` is `validate_access`'s `CapabilityOperation::HttpRequest` arm (`capability.rs:173-181`) — and nothing in the workspace ever constructs a `CapabilityOperation::HttpRequest` to call it. `network_scope` is parsed, stored, and never read by anything. A plugin manifest can declare `"external_http": true` today and the declaration is pure decoration — not "enforced but unused," genuinely unenforced. (Folded in from a sibling research session that checked whether a plugin could let flat peers act as NAT relays for each other: the answer is **no**, by absence rather than by design, since plugins have no network surface wired to anything at all — see §6 OD-1 and §9.)
- **The WIT contract and the running ABI are two different things.** `fe-plugin/wit/hexon-plugin.wit:124-128`'s `fractal-plugin` world imports `node-api`, `plugin-log`, `query-api`. `fe-plugin/src/AGENTS.md:131` calls this "the aspirational contract, not the wired ABI": the actual host registers core-ABI `func_wrap` imports (`wasm/host_imports.rs`) with `-1`/no-op denial sentinels on a failed or denied call (`host_imports.rs:170,195-196,223,253-254,280-281,306`), and no component-model bindgen exists to connect the two. A third party reading the WIT file today would reasonably assume it is the live contract. It isn't.
- **`fe-plugin → fe-sdk` is already done** (correcting a stale "standing gap" in prior notes): `fe-plugin/Cargo.toml:12` depends on `fe-sdk`, `fe-plugin/src/lib.rs:27-32` re-exports the SDK's stable types, and `AGENTS.md` §type-unification documents the migration as complete. No work item needed here.
- **`extensions/iot-bridge` is not a workspace member.** Its `Cargo.toml:1` carries its own `[workspace]` table (standalone build, confirmed by the root `Cargo.toml`'s member list not listing it), and it pins `rhai = "1.24"` (`extensions/iot-bridge/Cargo.toml:11`) against `fe-plugin`'s `rhai = "1.19"` (`fe-plugin/Cargo.toml:14`) — a real version skew between the host and its own reference example.

## 3. Scope, non-goals, and the boundary side

**In scope** (all open capability, all in this repo): the six phases in §4 — host thread behind an opt-in gate, publisher-signed packages, capability-consent UX, install-from-registry, the first-party terrain extension actually loading, and iot-bridge joining the workspace with an aligned rhai version.

**Non-goals (hard):**
- No pricing, revenue, payment, or marketplace business logic anywhere this track touches. This repo describes open capability only — host, signed package format, install flow, generic extension seams.
- No listing/review pipeline, no publisher verification queue, no counter-signing authority, no revocation-list *publishing* (only *honouring* a signed list published by whoever holds a revocation-capable trust root — see §4 revocation).
- No P2P/NAT-relay capability for plugins. Resolved, not deferred: the iroh `Endpoint` lives entirely inside the sync thread; plugins get no network surface here. Relay advertising is the public `relay_operability_20261031` track's `S-RELAY-ADVERTISE` seam, unrelated to this one.
- No hosted registry service and no account system. This track does not modify the reference registry (`fe-hexon-registry`); its default-deny auth change belongs to `hexon_entitlements_20261031` (today it runs open when `FE_REGISTRY_TOKEN` is unset).

**Boundary side:** listing/review automation, publisher verification, counter-signing authority and its key management, and revocation-list *publishing* sit outside this repository (`conductor/open-core.md` §The rule). Nothing such an operator does should ever require a change to this repo's public API beyond the seam contracts fixed in §4 — if it does, that is itself a signal the seam was drawn in the wrong place.

## 4. Design

All work sits inside `conductor/open-core.md`'s canonical seam **S-PLUGIN**: *"Publisher-signed plugin packages (ed25519 over manifest + payload hash), configurable trust roots, a signed revocation list."* This spec makes that sentence real, phase by phase:

- **Phase 0 — wasmtime + advisories.** Bump `wasmtime` past 29 (`fe-plugin/Cargo.toml:15`) far enough to retire some fraction of the 19 ignored RUSTSEC ids in `deny.toml:79-97`; whatever remains gets a fresh reason string (not "dormant" — see tripwires). Must land *before* Phase 1 makes the host live, since every one of those advisories graduates from theoretical to real the moment a thread executes untrusted WASM.
- **Phase 1 — opt-in host thread + close the enforcement gap.** `fractalengine`/`fractalengine-relay` gain `fe-plugin` as a dependency behind a Cargo feature, gated again at runtime by an env flag (OD-4), mirroring the existing `FE_API_SCREENSHOT_ALLOW` deny-by-default idiom already in this codebase. When enabled: spawn thread 7 (`PluginManager` + `PluginRegistry` as a Bevy resource), construct `fe_sdk::ui::UiExtensionRegistry` in `fe-ui`, and **call** `fe_terrain::extension::register_terrain_ui` so the first-party extension actually appears — closing the gap in §2. In the *same* phase, close OD-1: either wire `network_scope`/`external_http` into a real enforcement point (deny-by-default, no grant path) or delete the fields from `CapabilityManifest` until there is an enforcement point to attach them to. Mount `fe-terrain`'s `ApiExtensionHandle` routes into the real `fe-api` router so the doc comment in `fe-sdk/src/api.rs:4-5` stops being aspirational.
- **Phase 2 — publisher-signed package format.** Replace `lifecycle.rs::install_plugin`'s BLAKE3 self-check (`:80-90`) with ed25519 verification: the publisher signs `manifest_bytes || blake3(payload)`, the host verifies against a configurable set of trust-root public keys (OD-3), and an unsigned or untrusted-key package is refused *unless* an explicit dev flag is passed (and that flag must never be reachable from a release build — tripwire). The package carries a *list* of `{key_id, signature}` entries over the same bytes, and the host accepts it when at least one entry verifies against a trust root; that lets a second party (an organisation, a catalogue reviewer) counter-sign an already-published package without a format change, and whether a host requires a particular signer is trust-root policy (OD-3), not format. This is the exact replacement `AGENTS.md` §lifecycle already flags as needed.
- **Phase 3 — capability-manifest consent UX.** `fe-ui` gains an install dialog that renders the manifest's verse/petal/property scope and named capabilities (including, post-OD-1, whatever `network_scope` resolves to) before the Install action is enabled. No plugin activates silently.
- **Phase 4 — install-from-registry.** Fetch a package over **registry protocol v1** (defined by the sibling public track `hexon_entitlements_20261031`, which also defines the `PackageStore` trait and `EntitlementVerifier`). The client first checks the registry's version marker (`X-Hexon-Registry-Protocol: 1` response header, or `protocol_version` on `/health`; there is no versioned route prefix) and refuses a mismatch. It then verifies the Phase 2 signature, refuses any `(package_id, content_hash)` on a trusted revocation list, and — for a licensed package (`fe_format::license::License` with `LicenseType::Paid`) — verifies an entitlement token through the *same* `fe_format::entitlement::EntitlementVerifier` hexons use. The token's `package_id` is the plugin package id and its `content_hash` is the same payload hash the publisher signature covers; the payload is encrypted with the content key exactly like a licensed hexon entry. No new verification code; this phase is a new call site onto an existing, reused verifier. How a plugin package rides the registry wire is OD-9.
- **Phase 5 — iot-bridge as a workspace example.** Fold `extensions/iot-bridge` into the root workspace's `members` and resolve the rhai 1.19/1.24 skew to one pinned version shared by the host and its own reference extension.
- **Revocation (a public wire contract; external list publishers implement it byte-for-byte):** the host becomes a **consumer** of a signed revocation list, never a publisher. Shape: a JSON document `{ schema_version: 1, issued_at, entries: [{package_id, content_hash, reason, revoked_at}], signer_key_id, signature }`, where `signature` is ed25519 over the canonical (sorted-key) JSON of `entries`+`issued_at`. It is verified against the **same trust-roots file** Phase 2 uses (one key hierarchy), but only entries marked `revocation = true` may sign a list — a key trusted only to sign its own packages can never revoke someone else's (OD-3). Transport is OD-8 (recommended: pull from a URL configured beside each revocation-capable trust root, keeping the last good list cached so the host stays offline-capable). **Scope — one model shared with S-ENTITLEMENT:** this list is a *package-level* kill switch for withdrawn or malicious packages. It never revokes a licence; licence revocation for licensed plugins is token expiry plus refused reissuance, exactly as for hexons (`hexon_entitlements_20261031` spec §3, §4.5). The host's obligation ends at: refuse activation of any installed `(package_id, content_hash)` pair that appears in a list signed by a revocation-capable trust root. It never decides *why* something was revoked and never calls out to anywhere to ask permission to keep running already-active instances — that policy belongs to whoever configures the trust roots.

## 5. Acceptance criteria (observable, via real flows)

- **AC-1 (default-off):** with the opt-in flag unset, `fractalengine` and `fractalengine-relay` boot with no `PluginRegistry` resource and no plugin thread — `app.world().get_resource::<fe_plugin::registry::PluginRegistry>()` is `None`. Real flow: boot the actual app, no mocks.
- **AC-2 (host actually loads the terrain extension):** with the flag set, one `Update` tick after startup, `UiExtensionRegistry::total()` includes the terrain extension's 3 contributions and `get_by_slot(UiSlot::InspectorSection)` contains "Terrain Config" — the regression test for the §2 "never called" finding.
- **AC-3 (network capability honesty):** a manifest with `external_http: true` either successfully drives a real outbound call path that is observably gated (table: `none`/`local`/`internet` × attempted request → allow/deny) or the field no longer exists in the parsed manifest. No third state where it parses, looks enforced, and isn't.
- **AC-4 (signed packages):** a package signed by a trust-root key installs; the same payload signed by an unlisted key is refused with a typed error; an unsigned package is refused by default and only proceeds with the explicit dev flag, which must itself be logged loudly (`tracing::warn!`) every time it fires.
- **AC-5 (consent UX):** the install dialog renders the manifest's capability list before Install is enabled; a test asserts Install is disabled until the dialog has rendered that list at least once for the pending manifest.
- **AC-6 (install-from-registry):** against a real running `fe-hexon-registry` instance (not a mock — matches this repo's existing test-harness convention) serving a signed, unlicensed package, the install flow completes end to end; a licensed (`LicenseType::Paid`) package without a valid entitlement is refused by the *existing* `EntitlementVerifier` path with no new verifier code added here.
- **AC-7 (iot-bridge):** `cargo check -p iot-bridge` succeeds as a root workspace member on one pinned rhai version; `extensions/iot-bridge/tests/bridge_loop.rs` still passes unmodified.
- **AC-8 (WIT honesty):** either `wit/hexon-plugin.wit` carries an explicit `UNSTABLE` header pointing at `wasm/host_imports.rs` as the real ABI, or bindgen now wires the two together and `AGENTS.md:131`'s "aspirational" sentence is deleted because it is no longer true. Pick one; the contradiction cannot survive this track.

## 6. Open decisions

- **OD-1 — network_scope/external_http.** *Recommended default:* enforce deny-by-default with no grant path in v1 (no plugin can request outbound network access through this manifest field yet); add the enforcement point later as its own small change. *Reversal cost: low* — nothing depends on the current unenforced fields; tightening later is additive, loosening later is the only expensive direction.
- **OD-2 — WIT vs wired ABI.** *Recommended default:* mark the WIT `UNSTABLE — non-normative, tracks wasm/host_imports.rs by convention only` until component-model bindgen exists; revisit before any external/third-party plugin publishing is advertised. *Reversal cost: low now, medium once third parties have built against a WIT assumed stable.*
- **OD-3 — trust-root config shape.** *Recommended default:* a simple allow-list file (`trusted_publishers.toml`: key id → ed25519 public key, plus a per-entry `revocation = true|false` flag, default false) loaded at host startup, no dynamic registration in v1. *Reversal cost: medium* — a later move to a richer key-management format needs a migration, but the verification call site itself doesn't change shape.
- **OD-4 — opt-in mechanism.** *Recommended default:* both a compile-time Cargo feature (default off) and a runtime env flag, matching the screenshot-gate precedent (`FE_API_SCREENSHOT_ALLOW`). *Reversal cost: low.*
- **OD-5 — wasmtime bump timing.** *Recommended default:* Phase 0, strictly before Phase 1 wires the thread live. *Reversal cost: low* — an isolated `Cargo.toml` bump plus API fixups, independent of the other phases.
- **OD-6 — consent UX surface.** *Recommended default:* a modal dialog (not a passive panel) — Install stays disabled until the manifest has rendered. *Reversal cost: low.*
- **OD-8 — revocation-list transport.** *Recommended default:* pull — the host fetches the list from a URL configured beside each revocation-capable trust root on startup and on an interval, verifies it, and keeps the last good list cached so an unreachable URL never disables already-verified state. *Reversal cost: low → medium* — a push message would be a registry-protocol-v1 addition owned by `hexon_entitlements_20261031`.
- **OD-9 — plugin package shape on the registry wire.** *Recommended default:* a sealed `.hexon` with a new `HexonType::Plugin` (fe-format `manifest.rs`), carrying the plugin manifest + payload, the Phase 2 publisher signature, and an optional `fe_format::license::License` block — so registry protocol v1, `PackageStore`, and S-ENTITLEMENT apply with no new routes. The alternative is a separate `/api/v1/plugins/*` route family, which is a registry-protocol change owned by `hexon_entitlements_20261031`. *Reversal cost: medium* — published packages would need re-wrapping. A `HexonType` addition sequences after `hexon_entitlements_20261031`'s format-spec 1.1.0 bump.
- **OD-7 — rhai alignment direction.** *Recommended default:* bump `fe-plugin`'s `rhai` to iot-bridge's `1.24` rather than the reverse, since the host should track the newer line and the example is the thing meant to be forkable by third parties. *Reversal cost: low* — a version bump plus a recompile-and-fix pass, no API redesign expected.

## 7. Risks

- **Advisories go live.** The 19 wasmtime RUSTSEC ignores in `deny.toml` are justified today by "dormant." The moment Phase 1 lands without Phase 0 first, that justification is false while the ignores remain — mitigated by sequencing (§4, tripwires).
- **Unaudited sandbox, now exercised.** SECURITY.md already states the plugin sandbox has had no external audit. Reviving it raises the stakes of that gap from theoretical to real; the review-and-fix phase's mandatory `/security-review` is non-negotiable, not a formality.
- **A capability that looks enforced but isn't is worse than one that's visibly absent.** This is why OD-1 is scoped into Phase 1 itself rather than left as a follow-up — a shipped-and-forgotten unenforced capability is a classic "gate built, not wired" finding (cf. the 2026-07-31 security audit's pattern of exactly this failure mode elsewhere in the codebase).
- **WIT/ABI divergence could mislead a third-party implementer** into shipping a component against a contract the host doesn't actually speak. OD-2 must resolve before any public messaging implies third-party WASM plugins are pluggable today.
- **Wire-contract drift.** The revocation-list format (§4) is a public contract that external list publishers implement without visibility into this repo's change history. Version it by `schema_version`, never change v1 in place, and document it in `fe-plugin/src/AGENTS.md`; a silent format drift breaks the kill-switch invisibly.
- **Scope creep risk.** Because external services build on this seam, there will be pressure to let business-shaped concerns (feature tiers, "premium" capability flags) leak into this repo. Treat any such PR as an automatic non-goal violation (§3).
